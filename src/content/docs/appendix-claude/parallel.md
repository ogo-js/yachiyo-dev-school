## このページでできるようになること

- セッションをまたいで、作業を引き継げる
- サブエージェントに、読む作業や結果の検証をその場で任せられる
- いくつかのセッションに役割を分け、セッションどうしでやり取りさせられる

かかる時間の目安は60分です。

## 始める前に

付録の「道具を足す」を終えている必要があります。

## なぜこれを覚えるのか

付録の「Claude Code と話す」で、コンテキストには上限があり、いっぱいになると前の指示が落ちることを学びました。実際の仕事は、1つのセッションで終わらない作業や、たくさんのファイルを読む作業がほとんどです。何も考えずに1つのセッションで進めると、すぐにコンテキストが埋まります。

コンテキストを汚さずに作業を進める方法が3つあります。

| 方法 | すること |
| --- | --- |
| 引き継ぐ | セッションをまたいで、必要なことだけを持ち込む |
| サブエージェントに任せる | 作業の一部を別の担当者に任せ、まとめだけを受け取る |
| セッションに役割を分ける | いくつかのセッションを並べて動かし、メッセージでやり取りさせる |

## セッションを引き継ぐ

### 前のセッションの続きから始める

セッションの会話は手元に記録として残っています。ターミナルから、次のように打つと続きから始められます。

| 打つもの | すること |
| --- | --- |
| `claude -c` | このフォルダで直前に使ったセッションの続きから始める |
| `claude -r` | 前のセッションの一覧から選んで、続きから始める |

動いているセッションの中で `/resume` と打っても、一覧から選べます。

ただし、続きから始めると、前の長い会話もそのままコンテキストに戻ってきます。前の作業がかなり長かったときは、次の引き継ぎのメモを使うほうがすっきりします。

### 引き継ぎのメモを残す

長い作業は区切りのよい所でメモを書かせてから、新しいセッションで続けます。人が仕事を引き継ぐときと同じです。

```text
ここまでの作業を、次のセッションに引き継ぐメモにまとめて、NOTES.md に書いて。
やったこと、決めたこととその理由、残っていること、気を付けることを分けて書いて。
```

新しいセッションでは最初にこう頼みます。

```text
NOTES.md を読んで、続きの作業を始めて。
```

メモは自分でも読み、間違いがないか確かめてください。チームで共有したい決定事項はプルリクエストの説明やドキュメントに移します。自分だけの作業メモなら、`.gitignore` に書いて Git に入れないようにします。

## サブエージェントに任せる

サブエージェントは、Claude Code が作業の一部を任せる、別の担当者のようなものです。任された作業を自分のコンテキストの中で進め、終わったら結果のまとめだけを返します。メインの会話に残るのはまとめだけなので、コンテキストが埋まりません。

サブエージェントは、その場で任せるのが基本です。何も用意しなくても、Claude Code が作業の指示を書いて、最初から入っているサブエージェントに渡します。終わったら消える、使い捨ての担当者です。

### 読む作業を任せる

たくさんのファイルを読むと、それだけでコンテキストが埋まり、最初に伝えた指示が押し出されてしまいます。読む作業はサブエージェントに分けて任せ、メインの会話では結果だけを受け取ります。

```text
コードを全部自分で読むと最初の指示を忘れるので、読むのはサブエージェントに任せて。
画面・API・テストのように意味のある単位に分けて、それぞれ別のサブエージェントに読ませて、まとめだけ返して。
```

分けて任せると、それぞれのサブエージェントは自分の担当だけを読むので、見落としも減ります。

### 結果を確かめさせる

Claude Code が出した結果を、別のサブエージェントに確かめさせることもできます。

```text
api1 の SQL をレビューして。レビューした結果はサブエージェントに検証させて。
```

サブエージェントはメインの会話の中身を知らずに動きます。そのため、メインの会話でできあがった思い込みに引きずられずに、指摘が本当に正しいか、見落としがないかをまっさらな目で確かめられます。人の仕事で、作った人とは別の人に確かめてもらうのと同じ考え方です。

:::caution
確かめるのも AI です。検証の結果も、最後は自分で読んで判断してください。
:::

### 自分で作っておく

同じ観点の検証やレビューを何度も頼むようになったら、その指示をサブエージェントとして保存しておけます。`.claude/agents/` の下に Markdown のファイルを置きます。

```markdown
---
name: sql-reviewer
description: C# の API の SQL を見直す。API の SQL を書いたり直したりした後に使う。
tools: Read, Grep, Glob
---

あなたは SQL を見直す担当です。指定された C# のファイルの SQL を読み、次の点を確かめて、問題のある所をファイルの名前と行で報告してください。

- 値を SQL の文字に直接つなげず、パラメーターで渡しているか
- UPDATE と DELETE に WHERE が付いているか
- SELECT * を使わず、列の名前を並べているか

ファイルは直さず、報告だけをしてください。
```

- `name`：名前。「sql-reviewer で見直して」のように、名前で頼める
- `description`：どんなときに任せるか。Claude Code はこれを見て、自分から任せることもある
- `tools`：使ってよい道具。ここでは読むことと探すことだけにして、ファイルを直せないようにしている
- その下の文：サブエージェントへの指示

最初から作り込む必要はありません。その場で任せる使い方を続けて、同じ指示を何度も書いていると気づいたら作る、くらいで十分です。

## セッションに役割を分ける

ターミナルを2つ以上開けば、それぞれで別のセッションを動かせます。セッションどうしはメッセージでやり取りできます。

サブエージェントとの違いは、セッションは使い捨てではないことです。自分も直接話しかけられ、作業が終わっても残ります。長く続く役割を持たせたいときに向いています。

### 役割を分ける例

たとえば、次のように分けます。

| セッション | 役割 |
| --- | --- |
| 1つ目 | 画面を直す |
| 2つ目 | 1つ目が出した変更をレビューし、問題があれば知らせる |

1つ目のセッションで、次のように頼みます。

```text
ここまでの変更のレビューを、もう1つのセッションに頼んで。指摘が来たら直して。
```

Claude Code は同じパソコンで動いているほかのセッションを探し、相手に向けたメッセージを自分で書いて送ります。受け取ったセッションには「別のセッションからのメッセージ」として届きます。

- 送られるのは、Claude Code が書いたメッセージの文だけです。会話の記録やファイルがそのまま送られるわけではありません
- 届いたメッセージで、許可を求める画面に答えることはできません。許可は、そのセッションの前にいる人が出します
- どのセッションにやり取りできるかは、`/list-agents` で見られます

:::caution[同じファイルを同時に直させない]
2つのセッションに同じファイルを直させると、片方の変更がもう片方の変更を上書きしてしまいます。レビューの役のセッションには直させない、触るフォルダを分ける、ブランチ（第2部）を分ける、のどれかで分けてください。
:::

## 3つの方法の使い分け

| | サブエージェント | 別のセッション | 引き継ぎのメモ |
| --- | --- | --- | --- |
| 続く長さ | その作業だけ（使い捨て） | 自分で止めるまで | 次のセッションへ |
| 自分が話しかけられるか | できない | できる | ― |
| 向いているもの | 読む作業、結果の検証 | レビューの役など、長く続く役割 | 1つのセッションで終わらない作業 |

## 困ったとき

- **サブエージェントの結果が的外れ**：サブエージェントは会話の中身を知りません。頼むときに、何を、どこまで調べてほしいかを具体的に書いてください。
- **もう1つのセッションにメッセージが届かない**：`/list-agents` で、相手のセッションが一覧に出ているか確かめてください。出ていないときは、相手のセッションが動いているか、同じパソコンで動いているかを確かめてください。
- **2つのセッションの変更がぶつかった**：Git の差分で確かめ、ぶつかった所は第2部のコンフリクトと同じように直してください。

## 確かめよう

1. 「画面・API・テストに分けて、それぞれ別のサブエージェントに読ませて、このアプリの作りをまとめて」と頼む
2. 「api1 の SQL をレビューして。レビューした結果はサブエージェントに検証させて」と頼む
3. ターミナルをもう1つ開いて Claude Code を動かし、1つ目のセッションから「`rr1` の変更のレビューを、もう1つのセッションに頼んで」と頼む
4. 作業の区切りで引き継ぎのメモを書かせ、`/clear` してからメモを読ませて、続きを頼む

1で画面・API・テストのまとめが返り、2でレビューの指摘とその検証の結果が返り、3で2つ目のセッションにメッセージが届いてレビューが始まり、4でメモをもとに続きの作業が始まれば完了です。
