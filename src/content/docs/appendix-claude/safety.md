## このページでできるようになること

- 許可の仕組み（パーミッションモード）を知り、作業に合わせて切り替えられる
- AI がしがちな間違いを知り、出てきた変更を確かめられる
- 人に見せてはいけない情報を、AI に渡さないようにできる

かかる時間の目安は30分です。

## 始める前に

付録の「作業を分ける」を終えている必要があります。

## なぜこれを覚えるのか

Claude Code はファイルを直し、コマンドを打てます。とても便利ですが、間違ったときの影響も大きくなります。AI が作ったものの責任を持つのは、使った人です。

## 許可の仕組み

Claude Code には、どこまで自分で判断して進めてよいかを決める「パーミッションモード」があります。動かしている間に Shift キーを押しながら Tab キーを押すと、切り替わります。今のモードは入力欄の下に表示されます。

| モード | 聞かずにしてよいこと | 向いている場面 |
| --- | --- | --- |
| Manual | 読むことだけ | 1つずつ自分で確かめたいとき |
| accept edits | 読むことと、ファイルの書き換え | 書き換えを、後で差分でまとめて確かめるとき |
| plan | 読むことと調べることだけ。直す前に計画を出す | 直す前に、何をするつもりか確かめたいとき |
| auto | ほぼすべて。別の仕組みが、危ない操作を見張る | 長い作業で、確認の手間を減らしたいとき |

最初は auto で始まることが多くなっています。auto でも、危ない操作は見張りの仕組みが止めますが、公式の説明でも「安全を保証するものではない」とされています。慣れないうちや、大事な作業のときは、plan で計画を確かめてから進めるのがおすすめです。

## AI がしがちな間違い

AI はもっともらしい間違いをします。特に、次のことに気を付けてください。

| しがちなこと | どうするか |
| --- | --- |
| テストが通らないとき、コードではなく、テストの期待する値のほうを書き換えて通してしまう | テストのファイルの差分を必ず見る。CLAUDE.md に「テストの期待する値は勝手に変えない」と書いておく |
| 頼んでいない所まで直す | 「この関数だけ直して」のように範囲をはっきり頼む。差分で関係のない変更がないか見る |
| ないもの（関数、コマンドの指定、設定の項目）を、あるかのように書く | 動かして確かめる。知らない書き方は、公式の説明で確かめる |
| 自信のある言い方で、間違ったことを説明する | 大事なことは、根拠（ファイルの場所、公式の説明）を聞く。結果をサブエージェントに検証させる（作業を分ける） |
| 長い作業の途中で、前の指示を忘れる | 作業を小さく分け、1つ終わるごとに `/clear` する |

## 出てきた変更を確かめる

AI が直したものは、人が書いたものと同じように確かめます。第2部から第10部で覚えたことが、そのまま使えます。

1. `git diff` で、何が変わったかを1行ずつ読む（レッスン2-1）
2. 型の検査とテストを動かす（第6部、第9部）
3. 画面や API を実際に動かして、頼んだとおりに動くか確かめる
4. プルリクエストで人に見てもらう（レッスン2-5、10-2）

「AI が書いたので大丈夫」はありません。読んで分からないコードは、分かるまで説明させるか、使わないでください。

:::tip[こまめにコミットする]
AI に作業を頼む前に、今の状態をコミットしておきます。うまくいかなかったときに、`git restore` や `git switch` で、頼む前の状態にすぐ戻せます（第2部）。
:::

## 渡してはいけない情報

AI に頼むと、読んだファイルやコマンドの結果が、AI のサービスに送られます。次のものは AI に読ませたり、チャットに貼ったりしないでください。

- パスワード、API のキー、トークンなどの秘密の情報
- 個人の情報や、仕事で預かっている情報
- 会社や組織の決まりで、外に出してはいけないとされている情報

秘密の情報は `.env` のようなファイルに分け、Git にも入れないようにしておきます。仕事で使うときは、どの情報を AI に渡してよいか、組織の決まりを確かめてください。

## 困ったとき

- **思っていない所まで直された**：コミットしてあれば、`git restore` で戻せます。次からは plan のモードで計画を確かめてから進めてください。
- **AI の説明が正しいか分からない**：根拠を聞き、公式の説明や、実際に動かした結果で確かめてください。

## 確かめよう

1. `~/practice/business-app` で、今の状態をコミットする
2. plan のモードに切り替え、「社員の一覧に、給料の高い順に並べ替えるボタンを足したい」と頼む
3. 出てきた計画を読み、どのファイルをどう変えるつもりかを確かめてから進めさせる
4. 終わったら `git diff` を読み、型の検査とテストを動かす

4で、変更が計画どおりのファイルだけにとどまり、型の検査とテストが通れば完了です。

## 今は知らなくてよいこと

- 許可のきまりを、設定のファイルに細かく書く方法
- 操作のたびに自動で決まった処理を動かす仕組み（hooks）
